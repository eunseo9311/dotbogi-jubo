- 공개 주소: https://eunseo9311.github.io/dotbogi-jubo/ (첫 화면은 가장 최근 주보, 지난 주보는 `/YYYY-MM-DD/`)

## 0. 꼭 지킬 것

1. 사용자에게 하는 말은 모두 한국어로 쓴다. 사용자는 영어를 모른다.
2. 대조 검사(5단계)를 통과하지 못하면 올리지 않는다. 무엇이 문제였는지 알리고 끝낸다.
3. 개인정보는 넣지 않는다. 결혼·장례·새가족 명단의 이름, 010 휴대폰 번호, 계좌번호, 입금자명 예시가 여기에 해당한다. 예배 순서에 이름이 나오는 분(목사·장로·권사 등 인도자와 기도자)은 넣는다. `build.py`가 010 번호와 계좌번호 모양의 숫자를 막지만, 사람 이름은 직접 걸러야 한다.
4. 주보 사진은 저장소에 올리지 않는다. `work/`는 `.gitignore`에 들어 있다.
5. 서브 에이전트를 띄울 때는 `model: "opus"`를 쓴다.
6. 사진에서 확실히 읽히지 않는 글자는 짐작해서 채우지 않는다. 더 크게 잘라 다시 보고, 그래도 모르겠으면 그 항목을 뺀다.

## 1. 새 주보가 있는지 확인

```bash
cd ~/Desktop/sarangAX/dotbogi-jubo
git pull --ff-only
python3 tools/fetch_bulletin.py
```

출력 JSON의 `status`에 따라 움직인다.

- `done`: 이미 만든 주보다. "새 주보 없음"을 한 줄로 보고하고 끝낸다.
- `incomplete`: 오늘 올라온 주보인데 사진이 6장보다 적다. 아직 올리는 중이라고 한 줄로 보고하고 끝낸다. 내일 다시 확인한다.
- `error`(종료 코드 2): 홈페이지 구조가 바뀌었을 수 있다. 사용자에게 알리고 끝낸다.
- `new`: 2단계로 간다.

특정 날짜 주보를 만들라는 지시를 받았으면 모든 `fetch_bulletin.py` 명령에 `--date YYYY-MM-DD`를 붙인다.

- 표에서 칸이 여러 부에 걸쳐 합쳐져 있는지 본다. 예: 찬송 세 곡이 1~3부 칸에만 걸쳐 있고 4부 칸은 따로 있으면, 4부는 다른 곡이다.

## 3. 내용 파일 쓰기: `data/YYYY-MM-DD.json`

`data/`에서 날짜가 가장 큰 파일을 열어 구조를 그대로 따라 새 파일을 만든다. 필드 이름과 모양은 바꾸지 않는다.

### 화면 1: 예배 순서

| 필드 | 쓰는 법 |
|---|---|
| `date` | `YYYY-MM-DD`. 파일 이름과 같아야 한다 |
| `source_images` | 받은 사진 주소 목록 |
| `sermon.kicker` | 설교 칸의 머리말을 쉬운 말로. 예: 〈명절 특별메세지〉 → "추석 특별 설교". 없으면 "이번 주 설교" |
| `sermon.title` | 설교 제목 그대로(따옴표 없이) |
| `sermon.passage` | "시편 139편 1~6절"처럼 풀어 쓴다. 시편만 '편', 나머지는 '장' |
| `sermon.preacher` | "오정현 목사" |
| `verses` | 표지의 말씀 구절을 한 글자도 바꾸지 않고, 절마다 `{text, ref}`로 나눈다 |
| `verse_plain` | 그 구절을 쉬운 말로 한두 문장. 뜻을 더하거나 빼지 않는다 |
| `steps` | 주일예배 표의 줄 순서를 따른다(찬양 → 기도 → 찬양대 → 설교). 표에 없는 순서(헌금, 축도 등)는 만들지 않는다. 찬양 칸은 `hymns`에 책 이름·장·곡명을 그대로 적고, 몇 부가 부르는 곡인지 `text`와 `note`에 밝힌다 |
| `services` | 부마다 `part`("1부"), `time`("오전 8시", 오후 12:00은 "낮 12시"), `pre`("찬양은 오전 7시 40분부터"), `facts`. `facts`에는 예배 인도(주보의 '사회'), 찬양 인도(따로 있을 때), 대표 기도, 찬양대(`lines`: 찬양대 이름, 「곡명」)를 넣는다 |
| `services_note` | 수어 통역 같은 도움 안내가 있으면 한 문장. 없으면 뺀다 |
| `confession` | 공동체고백을 문장마다 나눠 원문 그대로. 매주 같더라도 사진과 대조한다 |
| `weekday` | 주중집회 표를 옮긴다. `name`, `time`("수요일 저녁 7시 30분"), `lines`(인도자, 「제목」, "창세기 29장 31~35절"), 필요하면 `list`(새벽기도회 요일별 설교자, '예배 및 모임 안내'에서), `note`(어려운 말 풀이) |

### 화면 2: 소식과 기도

| 필드 | 쓰는 법 |
|---|---|
| `three` | 이번 주 가장 중요한 세 가지. `strong`에 날짜를 괄호 없이 쓴다("10월 4일 주일까지", "10월 19일 월요일부터 24일 토요일까지"). 조사가 붙으면 `strong` 안에 넣는다("…27일 화요일은"). `text`는 할 일 한두 문장. 어르신이 직접 참여하거나 꼭 알아야 할 것을 먼저 고른다 |
| `news` | 어르신에게 쓸모 있는 소식 6~10개를 날짜순으로. `tag`는 9자 안쪽의 짧은 날짜("10월 4일 주일", "11월 4일까지"), `title`은 짧게, `sub`(선택)는 한 줄 설명, `lines`는 3줄 이하, `ask`(선택)는 교회 사무실 번호(02-…)와 장소만 |
| `joy` | 결혼 몇 가정(날짜), 장례 몇 가정, 새가족 몇 명. 이름은 넣지 않는다. `contact_label`은 "경조사 연락", `contact`는 경조부 사무실 번호 |
| `prayers` | 주보 글 안에 "기도해 주십시오", "기도 부탁", "마음 모아" 같은 요청이 있는 것만 최대 3개. 주보에 없는 기도 제목은 지어내지 않는다 |

소식에서 빼는 것: 온라인 헌금 계좌, 직원 채용, 전문 사역팀 정기모임 대부분, 영어·일본어·중국어 예배 세부 내용, QR코드 안내(대신 문의 전화를 적는다).

### 문체

- 어르신이 바로 알아듣는 쉬운 말을 쓴다. 어려운 한자어는 풀어 쓴다(중보기도 → 남을 위한 기도, 미취학 → 학교 가기 전, 향유 → 마음껏 누림).
- 해요체와 합니다체를 자연스럽게 섞는다. 번역투("~에 대해", "~하는 것은 ~이다"), 이모지, 느낌표 남발은 쓰지 않는다.
- 날짜와 시간은 풀어 쓴다: "10월 4일 주일", "오전 9시 30분", 정오는 "낮 12시".
- 줄이다가 뜻이 바뀌면 안 된다. 누가 대상인지, 몇 부 이야기인지, 누가 신청할 수 있는지는 원문 그대로 지킨다.

## 4. 페이지 만들기

```bash
python3 tools/build.py
```

"검사 실패"가 나오면 메시지대로 JSON을 고치고 다시 돌린다. 성공하면 `YYYY-MM-DD/index.html`과 `index.html`(가장 최근 주보)이 새로 써진다.

## 5. 대조 검사 (반드시)

Agent 도구로 검증 에이전트를 따로 띄운다(`subagent_type: "verifier"`, `model: "opus"`). 파일은 고치지 말고 보고만 하라고 한다. 프롬프트에 넣을 것:

- 사진 경로 `work/YYYY-MM-DD/01.jpg`~`06.jpg`와 조각 폴더, 내용 파일 `data/YYYY-MM-DD.json`
- 할 일: JSON의 날짜, 요일, 시간, 사람 이름과 직분, 찬송 책·장·곡명, 찬양대와 곡명, 설교 제목, 성경 장절, 장소, 전화번호, 금액, 숫자를 사진과 하나씩 대조한다. 성경 구절과 공동체고백은 글자 그대로인지 본다. 요약하면서 뜻이 바뀐 곳(대상, 몇 부, 신청 자격)과 주보에 없는 내용을 찾는다. 결혼·장례·새가족 명단의 이름이나 010 번호가 들어갔는지 본다. 요일은 달력으로 확인한다.
- 일부러 한 것(쉬운 말로 바꾸기, 소식 고르기, 3줄 요약, 명단 대신 개수만 쓰기)은 뜻이 바뀌지 않았다면 문제 삼지 않는다.
- 보고 형식: "틀림(꼭 고칠 것)"과 "뜻이 달라짐(고치면 좋은 것)"으로 나눠 틀린 글, 주보 원문, 고칠 글을 적는다. 마지막 줄에 PASS 또는 FAIL.

보고를 받으면 틀린 곳을 모두 고치고 4단계를 다시 돌린다. 크게 고친 곳이 있으면 검사를 한 번 더 받는다. 끝까지 풀리지 않는 틀림이 있으면 올리지 않는다.

## 6. 올리기

```bash
git add data/YYYY-MM-DD.json index.html 20??-??-??/index.html   # 다른 주 페이지의 '다른 주 주보 보기' 목록도 함께 바뀐다
git commit -m "Add bulletin for YYYY-MM-DD" -m "<무엇을 옮겼고 무엇을 확인했는지 두세 줄, 영어>" -m "<시스템이 알려 주는 Co-Authored-By 줄>"
git push origin main
```

배포 확인은 Bash의 `run_in_background`로 아래 루프를 돌려 두고 끝났다는 알림을 기다린다. 사용자 셸은 zsh라서 `set -- $var`로 나누면 안 된다. 값은 변수마다 따로 받는다.

```bash
sha=$(git rev-parse --short=7 HEAD)
for i in $(seq 1 30); do
  st=$(gh api repos/eunseo9311/dotbogi-jubo/pages/builds/latest --jq .status)
  c=$(gh api repos/eunseo9311/dotbogi-jubo/pages/builds/latest --jq '.commit[0:7]')
  if [ "$st" = "built" ] && [ "$c" = "$sha" ]; then echo "READY $sha"; exit 0; fi
  if [ "$st" = "errored" ]; then echo "ERRORED"; exit 1; fi
  sleep 10
done
echo "TIMEOUT $st $c"; exit 2
```

끝나면 `curl -s "https://eunseo9311.github.io/dotbogi-jubo/?v=$RANDOM"`에 새 날짜("M월 D일 주일")가 들어 있는지 확인한다.

## 실패했을 때

어느 단계에서든 막히면(사진이 안 받아짐, 글씨를 읽을 수 없음, 검사에서 풀리지 않는 틀림, push 실패) 올리지 않는다. 만들던 파일은 커밋하지 않은 채로 두고, 무엇이 문제인지 한국어로 알린다. 다음 날 예약 작업이 같은 주보를 다시 시도한다(`data/YYYY-MM-DD.json`을 커밋하지 않았으므로 status가 계속 `new`로 나온다). 만들다 만 `data/YYYY-MM-DD.json`이 남아 있으면 다음 시도 때 지우고 처음부터 다시 쓴다.

## 나중에 서버로 옮길 때

사진 받기(`fetch_bulletin.py`)와 페이지 만들기(`build.py`)는 사람이나 AI 없이 도는 스크립트다. AI가 하는 일은 3단계(사진을 읽고 JSON 쓰기)와 5단계(대조 검사) 두 가지뿐이다. GitHub Actions로 옮기려면 매일 도는 워크플로에서 `fetch_bulletin.py`를 돌리고, `new`일 때 Claude API에 사진 6장과 이 문서의 3단계 규칙을 보내 JSON을 받고, 다른 호출로 5단계 검사를 한 뒤 `build.py`와 커밋을 하면 된다. Anthropic API 키는 저장소 Secrets에 넣는다.
